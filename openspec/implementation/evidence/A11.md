# A11 — 资源生命周期与取消（证据）

状态：核心运行时落地（serial admission、engine-owned bytes 账户、RAII 释放、跨 engine 拒绝、entry 级并行合并）。base `0842837`（A10）。集成 owner 本人实现（A11 subagent 多次停滞被终止）。

## 实现

1. **Runtime（Engine 共享运行时）**：`Engine { options, runtime: Arc<Runtime> }`；Clone 共账户。Runtime 含：
   - `admission: Mutex<()>` —— 顶层操作串行准入；等待方以 8ms 有界轮询检查自身 cancel flag/deadline（interfaces §5：可取消等待，FIFO 不承诺）。RAII `Admission` ticket：错误/取消/成功路径均释放。
   - `active_bytes: AtomicU64` —— engine-owned 活跃字节账户：open 时 fetch_add（输入全长保留），Artifact drop 时 fetch_sub 归还（RAII）。
2. **engine-bytes 限额**：`Limits.max_engine_owned_bytes`（默认 2GiB）；open 时立即拒绝（不等待其他 Artifact drop）——`ResourceLimit`。CLI `--limit engine-bytes` 从 accepted 升级为 **enforced**（同时修复 A08 遗留的静默忽略 bug：apply match 中 EngineBytes 落在 accepted 组）。
3. **跨 engine 拒绝**：操作校验 `Arc::ptr_eq(runtime)`，外来 Artifact → `InvalidQuery`。
4. **entry 级内部并行**：`fold_roots` 用 rayon `par_iter` 跨 entry inflate+validate+扫描；结果/错误按**中央目录序合并**——最低序错误即操作错误，输出与调度无关（interfaces §4）。解码预算 `AtomicU64`（`zip::read_entry` 改为 fetch_add + check）。
5. **取消检查点**（已有 + 本轮接线）：open 读取、每 ≤64KiB 解压拷贝、扫描每方法/每 ≤4096 code units、序列化每 item/64KiB、admission 等待轮询。Cancelled{User|Deadline} → CLI 130 并区分原因（A08）。

## 已知限制（如实）

- **内部并行为 entry 级**：单 entry 内的扫描为顺序（A03 扫描器未做类内并行）。per-method 池化留待后续（不影响正确性/确定性契约）。
- 后端（droidsaw）内部不可抢占阶段清单见 A04 evidence；deadline 为协作式。
- 不声称 RSS 硬限制： Limits 为协议级预算；QUAL-03 实测由 A14 完成。

## 测试（engine.rs tests 模块，含 2 个新增）

- `cross_engine_artifacts_are_rejected`：engine B 上操作 engine A 的 Artifact → InvalidQuery；本 engine 正常。
- `engine_owned_bytes_account_tracks_and_releases`：64B 预算拒开 → ResourceLimit 且账户为 0；放宽后 open 保留计数=字节长；drop 后归 0。
